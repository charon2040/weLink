## 2 模块设计

### 2.1 连接层 — WebSocketServer

**职责**：管理 WebSocket 长连接的生命周期。

**关键设计**：

- **Netty 线程模型**：1 boss + (ioThreads-1) worker + businessThreads 业务线程
  - boss 线程：接受新连接
  - worker 线程：处理 IO 读写（默认 16 线程）
  - business 线程：执行业务逻辑（默认 48 线程），避免阻塞 IO 线程
- **Pipeline 配置**：
  ```
  IdleStateHandler(300s) → HttpServerCodec → ChunkedWriteHandler
  → HttpObjectAggregator(64KB) → WebSocketServerProtocolHandler("/ws")
  → WebSocketChannelHandler(businessGroup)
  ```
- **连接参数**：
  - SO\_BACKLOG = 8192（TCP 半连接队列）
  - SO\_KEEPALIVE = true
  - WriteBufferWaterMark = \[64KB, 256KB]（写缓冲水位线）
- **WebSocketSession**：封装 Channel + userId + deviceId，提供帧级限流（500 req/s）

### 2.2 IM 核心 — IMService

**职责**：消息路由、认证、推送、限流的核心逻辑。

**关键设计**：

**2.2.1 消息类型路由**

```
handleMessage(ctx, json)
  ├── type="auth"      → handleAuth()       // JWT验证 + Redis路由写入
  ├── type="message"   → handleSendMessage() // 私聊/群聊分发
  ├── type="heartbeat" → handleHeartbeat()   // Redis TTL续期
  ├── type="ack"       → handleAck()         // 已读回执
  └── type="recall"    → handleRecall()      // 消息撤回
```

**2.2.2 认证流程**

1. 客户端发送 `{type: "auth", token: "jwt...", deviceId: "web"}`
2. 验证 JWT Token 有效性
3. 踢掉同一用户同一设备的旧连接
4. 写入内存映射：`onlineUsers[userId][deviceId] = session`
5. Redis Pipeline 批量写入：
   - `user:online:{userId}` → "online" (TTL 300s)
   - `im:route:{userId}:{deviceId}` → "instanceId:channelId" (TTL 300s)
   - `im:route:user:{userId}` → "instanceId" (TTL 300s)
6. 返回认证成功响应

**2.2.3 消息发送流程**

私聊：

```
客户端 WS → IMService.handleSendMessage()
  → publishPrivateIngress() → Kafka "im-private-ingress"
  → Consumer 持久化 + 本地推/Outbox
```

群聊（小群 ≤500 人，写扩散）：

```
客户端 WS → IMService.handleSendMessage()
  → publishGroupIngress() → Kafka "im-group-ingress"
  → Consumer → handleWriteDiffusionMessageBatch()
    → 持久化 + ForkJoinPool(32) 并行推 + Outbox(跨实例)
```

群聊（大群 >500 人，读扩散）：

```
客户端 WS → IMService.handleSendMessage()
  → publishGroupIngress() → Kafka "im-group-ingress"
  → Consumer → handleLargeGroupMessageBatch()
    → 持久化 + 本地推 + Kafka "im-large-group-message" 广播
    → 各实例 Consumer → 推本地在线用户
```

**2.2.4 限流策略**

| 层级               | 限流方式                | 阈值                   | 行为          |
| ---------------- | ------------------- | -------------------- | ----------- |
| WebSocketSession | 帧计数滑动窗口             | 500 req/s            | 丢弃超限请求，不关连接 |
| IMService 私聊     | Redis INCR + 2s TTL | 500 msg/s            | 返回错误提示      |
| IMService 群聊     | Redis INCR + 2s TTL | 300 msg/s/group/user | 返回错误提示      |

**2.2.5 在线用户管理**

- 内存：`ConcurrentHashMap<Long, ConcurrentHashMap<String, WebSocketSession>> onlineUsers`
  - 外层 Key = userId，内层 Key = deviceId
  - 支持同一用户多设备同时在线
- Redis 路由表：用于跨实例消息路由
  - `im:route:user:{userId}` → 实例 ID（聚合路由）
  - `im:route:{userId}:{deviceId}` → 实例ID:ChannelId（精确路由）

**源码位置**：[IMService.java](file:///g:/WeLink/src/main/java/com/epsilon/welink/im/service/IMService.java)

### 2.3 消息消费 — MessageConsumer

**职责**：消费 Kafka Ingress Topic，完成消息持久化和推送调度。

**Consumer Group 设计**：

| Topic                  | Consumer Group            | 并发数 | 说明             |
| ---------------------- | ------------------------- | --- | -------------- |
| im-private-ingress     | welink-im-private-ingress | 8   | 全局唯一，保证私聊消息顺序  |
| im-group-ingress       | welink-im-group-ingress   | 16  | 全局唯一，保证群消息顺序   |
| im-private-message     | welink-im-{instanceId}    | 4   | 每实例独立，确保所有实例收到 |
| im-group-message       | welink-im-{instanceId}    | 4   | 每实例独立          |
| im-large-group-message | welink-im-{instanceId}    | 3   | 每实例独立          |
| im-presence            | welink-im-{instanceId}    | 2   | 每实例独立          |
| im-recall              | welink-im-{instanceId}    | 2   | 每实例独立          |

**关键设计**：

- Ingress Consumer 全局唯一：保证同一会话的消息在同一分区有序
- Message Consumer 每实例独立：确保每个实例都能收到跨实例消息
- Kafka Key 策略：私聊用 conversationKey，群聊用 groupId，跨实例消息用 targetUserId

**源码位置**：[MessageConsumer.java](file:///g:/WeLink/src/main/java/com/epsilon/welink/im/consumer/MessageConsumer.java)

### 2.4 消息存储 — MessageService + AsyncBatchWriter

**职责**：消息持久化、inbox/outbox 写入、历史查询。

**2.4.1 AsyncBatchWriter**

- 内部队列：`LinkedBlockingQueue<Object>(10000)`
- 刷盘频率：每 100ms 执行一次 `flush()`
- 批量策略：每次最多 drain 200 条，按分片桶分组后批量 INSERT
- 降级：队列满时同步单条写入，避免消息丢失

**2.4.2 消息写入流程**

```
MessageService.buildAndEnqueuePrivateMessage()
  → 1. 构建 Message 对象（含 msgId, conversationSeq）
  → 2. INSERT message 表（按 conversation_id % 8 分库，按月分表）
  → 3. AsyncBatchWriter.submitInboxTask()（receiver 的 inbox）
  → 4. 若需 Outbox: AsyncBatchWriter.submitOutboxTask()
```

### 2.5 Outbox 发布 — MessageOutboxService

**职责**：轮询 outbox\_pending 索引表，将跨实例消息发布到 Kafka。

**2.5.1 核心流程**

```
OutboxPublisherScheduler (每 1s)
  → MessageOutboxService.publishDueEvents()
    → 1. Redis 分布式锁 (outbox:poll:lock:pending, 10s TTL)
    → 2. SELECT * FROM outbox_pending WHERE status IN (0,1)
         AND next_retry_at <= NOW() ORDER BY next_retry_at LIMIT 1000
    → 3. 按 outbox_shard 分组，HintManager 精确路由到 message_outbox 分片
    → 4. 加载 Message 内容
    → 5. 异步发送到 Kafka Topic
    → 6. 成功：删 pending 行 + 更新 outbox 状态为 PUBLISHED
    → 7. 失败：指数退避重试 (5s × 2^retryCount)，最多 6 次
```

**2.5.2 Redis Reconcile 补偿**

当 outbox\_pending INSERT 失败时：

1. 将 outboxId + targetUserId + topic + msgId 写入 Redis Hash（TTL 7 天）
2. 将 outboxId 加入 Redis SET `outbox:reconcile:set`
3. 定时任务 `reconcileMissedPending()` 读取 Redis SET，补写 outbox\_pending 行
4. 补写成功后清除 Redis 记录

**源码位置**：[MessageOutboxService.java](file:///g:/WeLink/src/main/java/com/epsilon/welink/message/service/MessageOutboxService.java)

### 2.6 降级管理 — DegradationManager

**职责**：5 级降级策略，保障核心功能在高负载下可用。

| 等级 | 描述     | 关闭功能      | 保留功能         |
| -- | ------ | --------- | ------------ |
| L0 | 正常模式   | 无         | 全部           |
| L1 | 关闭在线广播 | 好友在线状态推送  | 消息收发、已读回执、群聊 |
| L2 | 关闭已读回执 | + 已读回执处理  | 消息收发、群聊      |
| L3 | 关闭大群推送 | + 大群写扩散   | 消息收发（大群仅读扩散） |
| L4 | 关闭文件上传 | + 文件/图片上传 | 文本消息收发       |
| L5 | 仅文本模式  | + 所有辅助功能  | 仅文本消息收发      |

**管理接口**：

- `GET /admin/degradation`：查询当前降级状态
- `POST /admin/degradation/level/{level}`：设置降级等级

**源码位置**：[DegradationManager.java](file:///g:/WeLink/src/main/java/com/epsilon/welink/common/DegradationManager.java)

### 2.7 关系管理 — RelationService

**职责**：好友关系、群组管理。

**关键设计**：

- 好友申请：幂等控制（PENDING/ACCEPTED 状态不可重复申请，REJECTED 可重新申请）
- 群成员缓存：Redis 缓存群成员列表，减少数据库查询
- 群信息广播：group\_info 为 ShardingSphere 广播表，所有分片存全量

## 4 消息链路

### 4.1 私聊消息链路

```
发送者 WS ──→ IMService.handleSendMessage()
                │
                ├── Kafka "im-private-ingress" (key=conversationKey)
                │
                ▼
         PrivateIngressConsumer.consumePrivateIngress()
                │
                ├── MessageService.buildAndEnqueuePrivateMessage()
                │     ├── INSERT message (分片)
                │     ├── AsyncBatchWriter.submitInboxTask() → receiver inbox
                │     └── 若跨实例: AsyncBatchWriter.submitOutboxTask()
                │
                ├── IMService.dispatchPersistedPrivateMessage()
                │     ├── 本地在线? → pushToAllSessions() → 接收者 WS
                │     └── 跨实例? → Outbox → Kafka "im-private-message"
                │                                    │
                │                                    ▼
                │                           PrivateMessageConsumer
                │                                    │
                │                                    └── pushMessage() → 接收者 WS
                │
                └── 离线? → inbox 记录，上线后拉取
```

### 4.2 群聊消息链路（小群 ≤500 人，写扩散）

```
发送者 WS ──→ IMService.handleSendMessage()
                │
                ├── Kafka "im-group-ingress" (key=groupConversationKey)
                │
                ▼
         GroupIngressConsumer.consumeGroupIngress()
                │
                ├── IMService.processGroupIngressBatch()
                │     └── handleWriteDiffusionMessageBatch()
                │           ├── 持久化 Message + 批量 Inbox + Outbox
                │           ├── classifyWriteDiffusionRecipients()
                │           │     ├── 本地在线 → 直接推
                │           │     ├── 其他实例在线 → Outbox
                │           │     └── 离线 → Inbox 记录
                │           └── pushToGroupOnlineMembers()
                │                 └── ForkJoinPool(32) 并行推送
                │
                └── Outbox → Kafka "im-group-message" (key=targetUserId)
                                    │
                                    ▼
                           GroupMessageConsumer
                                    │
                                    └── pushMessage() → 各实例本地在线用户
```

### 4.3 群聊消息链路（大群 >500 人，读扩散）

```
发送者 WS ──→ IMService.handleSendMessage()
                │
                ├── Kafka "im-group-ingress"
                │
                ▼
         GroupIngressConsumer
                │
                ├── handleLargeGroupMessageBatch()
                │     ├── 持久化 Message（仅一条）
                │     ├── 本地在线用户 → 直接推
                │     └── 有跨实例在线? → Kafka "im-large-group-message"
                │                                    │
                │                                    ▼
                │                           LargeGroupMessageConsumer
                │                           (每实例独立 Consumer Group)
                │                                    │
                │                                    └── 推本地在线用户
                │
                └── 离线用户 → 上线后按 groupSeq 增量拉取
```

## 5 分布式设计

### 5.1 多实例部署

```
┌──────────────┐     ┌──────────────┐
│  Instance-1  │     │  Instance-2  │
│              │     │              │
│  Netty WS    │     │  Netty WS    │
│  Spring Boot │     │  Spring Boot │
│  Kafka C/G:  │     │  Kafka C/G:  │
│   welink-im- │     │   welink-im- │
│   instance-1 │     │   instance-2 │
└──────┬───────┘     └──────┬───────┘
       │                    │
       └──────┬─────────────┘
              │
     ┌────────▼────────┐
     │  Shared Redis   │ ← 路由表 + 限流 + 缓存
     │  Shared Kafka   │ ← 跨实例消息总线
     │  Shared MySQL   │ ← 分片数据存储
     └─────────────────┘
```

**关键机制**：

- Redis 路由表：`im:route:user:{userId}` 记录用户所在实例
- Kafka Consumer Group 隔离：每实例使用独立 Group ID，确保所有实例收到跨实例消息
- Outbox 模式：发送实例写入 outbox + pending，由 OutboxPublisherScheduler 定时发布到 Kafka
- 分布式锁：Redis SETNX 实现轮询锁，防止多实例重复发布
