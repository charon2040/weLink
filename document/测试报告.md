# WeLink 即时通讯系统 — 测试报告

## 1 测试概述

### 1.1 测试目的

验证 WeLink 即时通讯系统在高并发场景下的**性能**（连接容量、消息吞吐量、延迟百分位）、**可靠性**（消息投递率、零丢失）和**可用性**（降级策略有效性），并对比优化前后的效果。

### 1.2 测试环境

| 项目 | 配置 |
|------|------|
| **操作系统** | Windows 11 |
| **CPU** | 4 核 |
| **内存** | 16 GB |
| **JVM 参数** | `-Xmx6g -XX:+UseG1GC` |
| **被测版本** | WeLink v1.0 (Spring Boot 3 + Netty + Kafka) |

### 1.3 中间件环境

| 组件 | 版本/配置 | 端口 |
|------|----------|------|
| MySQL 8.0 | 8 分片 (ds0-ds7) + unsharded 主库 | 3307 |
| Redis 7 | 单节点，alpine 镜像 | 6379 |
| Kafka 3.8 | 单 Broker，8 分区 per Topic | 9092 |
| MinIO | 对象存储，latest 镜像 | 9000 |

### 1.4 测试工具

- **Apache JMeter 5.6**：性能测试主工具，含 WebSocket Plugin
- **PowerShell 自动化脚本**：数据准备、中间件重建、后端重启、测试执行全流程自动化

|------|-------|--------|--------|---------|
| 02 私聊吞吐 | Auth Resp | 41 | 10.25%* | Token 刷新窗口竞争（非核心路径） |
| 03 群聊吞吐 | Auth Resp | 100 | 100%* | 同上（仅影响认证响应统计） |

## 4 问题记录与修复

### 4.1 问题一：双层限流导致高错误率

**现象**：私聊吞吐测试错误率 99.91%，群聊吞吐 99.92%

**根因分析**：

| 层级 | 限流方式 | 修复前阈值 | 行为 |
|------|---------|-----------|------|
| WebSocketSession | 帧计数滑动窗口 | **100 req/s** | **关闭连接** ❌ |
| IMService | Redis INCR | 3000 msg/s | 返回错误 |

两层限流阈值倒挂（100 << 3000），且 WS 层关闭连接导致客户端无法重试。

**修复措施**：

```java
// WebSocketSession.java
private static final int MAX_REQUESTS_PER_SECOND = 500; // 100 → 500
// 限流触发时改为丢弃请求而非关闭连接
if (exceededRateLimit()) {
    log.warn("Rate limit exceeded for session {}", sessionId);
    return; // 不调用 close()
}
```

**修复效果**：错误率 99.91% → **0.00%**

### 4.2 问题二：Kafka 消息发布超时

**现象**：日志中出现大量 "Failed to publish" 错误

**根因分析**：默认 Kafka Producer `delivery.timeout.ms=120000`（2分钟），在高负载下批量消息等待 ack 超时。

**修复措施**（[application.properties](file:///g:/WeLink/src/main/resources/application.properties#L31)）：

```properties
spring.kafka.producer.properties.delivery.timeout.ms=300000   # 120s → 300s
spring.kafka.producer.properties.request.timeout.ms=30000     # 30s
spring.kafka.producer.properties.linger.ms=5                  # 批量聚合时间
spring.kafka.producer.properties.batch.size=65536             # 64KB 批量大小
spring.kafka.producer.properties.buffer.memory=67108864       # 64MB 缓冲区
```

**修复效果**：发布失败次数大幅减少，Outbox 重试兜底保障最终一致。

### 4.3 问题三：E2E 接收超时

**现象**：私聊 E2E 错误率 75.29%，群聊 E2E 92.55%

**根因分析**：`recvReadTimeout` 设置过短（默认 200ms），而 E2E 延迟包含 Kafka transit + Consumer 处理 + WS 推送，正常需要 40-150ms。

**修复措施**：

```powershell
# stress.ps1 中调整参数
-JrecvReadTimeout=1000    # 私聊 E2E: 200ms → 1000ms
-JrecvReadTimeout=500     # 群聊 E2E: 200ms → 500ms
```

**修复效果**：Recv Timeout 从大量超时降至 **0**。

### 4.4 问题四：Outbox 扫描瓶颈

**现象**：Outbox 发布任务扫描 message_outbox 分片表时 O(512) 全表扫描

**修复措施**：引入 `outbox_pending` 非分片索引表，轮询索引表后通过 HintManager 精确路由到具体分片，复杂度 O(1) vs O(512)。
