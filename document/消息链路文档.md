# WeLink 消息链路文档

## 1. 文档范围

本文档覆盖当前消息系统的真实实现：

- 私聊
- 群聊
- outbox 异步投递
- ACK / 已读 / 撤回
- 历史消息 / 离线消息 / 同步游标
- 在线路由与跨实例判断
- 限流与降级

## 2. 公共组件

### 2.1 WebSocketSession 背压

`WebSocketSession.writeAsync()` 当前不是旧版“独立写线程 + 写队列”模型，而是基于：

- `channel.isActive()`
- `channel.isWritable()`
- `writeAndFlush(new TextWebSocketFrame(...))`

这意味着当前背压策略是 Netty 可写性检查，不是历史文档里那种自建 `LinkedBlockingQueue` 模型。

### 2.2 conversation_id

`conversation_id` 是消息主表的核心分片键。

规则：

- 私聊：`single:{minUid}:{maxUid}`
- 群聊：`group:{groupId}`
- 再由 `buildConversationId(convKey)` 生成稳定 long 值

作用：

- 把单会话消息尽量路由到固定分片
- 让历史查询、撤回、已读等路径尽量走单分片

### 2.3 在线路由

当前 Redis 路由分两层：

- 单设备路由：`im:route:{userId}:{deviceId}`
- 用户聚合路由：`im:route:user:{userId}`

设备级路由值形如：

```text
{instanceId}:{channelId}
```

### 2.4 `isUserOnlineOnOtherInstance`

当前实现已移除 SCAN 回退，仅依赖聚合键查询：

1. 查聚合键 `im:route:user:{userId}`
2. 如果拿到实例 ID，与当前实例比较
3. 如果聚合键不存在或读取失败，直接返回 `false`

`isUserOnlineOnOtherInstanceByScan` 方法已删除。群聊路由中（`classifyWriteDiffusionRecipients`、`hasAnyUserOnlineOnOtherInstance`）的 SCAN 回退也已移除，聚合键未解析的用户统一归入 `offlineIds`。

**原因**：SCAN 在高并发下遍历整个 Redis keyspace，每次耗时数百毫秒，严重阻塞 Kafka 消费者线程。单机部署场景下聚合键已足够判断路由。

## 3. 私聊链路

### 3.1 同实例在线

流程：

1. 服务端校验发送者权限和限流
2. 先写 `message`
3. 若目标用户在线且在本实例，直接推送 WebSocket
4. 发送端收到 ACK / 或通过后续同步补齐状态

### 3.2 跨实例在线

流程：

1. 发送端实例写 `message`
2. 判断目标用户在线但不在本实例
3. 写 `message_outbox`
4. 同步写 `outbox_pending`
5. 调度器扫描待发布记录并发 Kafka
6. 目标实例消费 `im-private-message`
7. 目标实例推送给本地在线 session

### 3.3 完全离线

流程：

1. 写 `message`
2. 写 `message_inbox`
3. 用户上线后通过离线消息或同步接口补拉

## 4. 群聊链路

### 4.1 小中群

当前小中群走写扩散：

- 本地在线成员：直接推送
- 其他实例在线成员：写 `message_outbox`
- 离线成员：写 `message_inbox`

### 4.2 大群

当前大群走读扩散：

- 先落主消息
- 更多依赖历史拉取、游标同步和按需获取
- 避免对大群所有成员同步写扩散

阈值：

- `welink.im.medium-group-threshold=100`
- `welink.im.large-group-threshold=1000`

## 5. inbox / outbox 批量优化

### 5.1 inbox

当前 `createInboxRecords()` 已按 `receiver_id % 64` 分桶：

- 同桶走批量插入
- 失败时退回逐条插入

这能降低小中群离线成员场景下的 SQL 条数。

### 5.2 outbox

当前 `createOutboxRecords()` 已按 `target_user_id % 64` 分桶：

- 同桶走批量插入
- 失败时退回逐条插入
- 已在真实双实例群聊压测中验证命中

### 5.3 消息持久化批处理（第5轮优化）

第5轮优化引入了消息持久化的批量漏斗模型，彻底将 consumer 线程与 MySQL 写入解耦：

**核心机制**：

```
16 consumer 线程 → offer 到 LinkedBlockingQueue(10000)
                     ↓
         定时器每 100ms 触发 / 满 1000 条触发
                     ↓
         drainTo(1000) → 8 shard 并行 batch INSERT
                     ↓
         8 线程并行 conversation UPDATE
                     ↓
         async batch inbox/outbox INSERT
```

**关键组件**：

| 组件 | 说明 |
|------|------|
| `messageBatchQueue` | LinkedBlockingQueue(10000)，消息缓冲漏斗 |
| `MessageMapper.insertBatch` | 单条 SQL 批量 INSERT 多行 message |
| `flushMessageBatch()` | drainTo(1000) + 8 shard ForkJoin 并行写 |
| `convUpdateExecutor` | 8 线程池，conversation UPDATE 并行 + 按 convId 去重 |
| `groupPushExecutor` | ForkJoinPool(32)，群成员 push fire-and-forget |

**效果**：consumer 每条消息耗时从 25ms 降到 ~2ms（只做 build + Redis + offer），p50 从 413ms 降到 8ms。

**Kafka 配置变更**：

- `im-private-ingress` partitions: 8 → **16**
- `im-group-ingress` partitions: 8 → **16**

## 6. ACK / 已读 / 撤回

### 6.1 ACK

客户端收到消息后会主动发 `ack`。

### 6.2 已读

会话切换或拉取完成后，前端通过 `/message/read/conversation` 更新会话已读状态。

### 6.3 撤回

撤回会优先走带路由信息的精确查询路径，不再依赖全分片广播查询。

## 7. 历史消息与同步

当前消息恢复依赖三条路径：

- `/message/history/private`
- `/message/history/group`
- `/message/sync`

其中 `/message/sync` 基于客户端持有的 cursor 做补齐，适合断线重连后的增量同步。

## 8. 限流与降级

### 8.1 限流

当前关键限流：

- 私聊：`welink.im.send-rate-limit-per-second=200`
- 群聊：`welink.im.group-rate-limit-per-second=100`

群聊限流是 **per-user-per-group**，不是 per-group 绝对量。

**心跳与在线状态配置**：

| 配置项 | 值 | 说明 |
|--------|----|------|
| `welink.websocket.heartbeat-timeout` | 120s | Netty IdleStateHandler 读空闲超时 |
| `ONLINE_TTL_SECONDS` | 120s | Redis `user:online:*` 键过期时间 |
| `ROUTE_TTL_SECONDS` | 120s | Redis `im:route:*` 键过期时间 |
| `HEARTBEAT_TIMEOUT_SECONDS` | 120s | 常量，与 heartbeat-timeout 对齐 |

客户端每 30s 发一次心跳 → 服务端 120s idle timeout → Redis TTL 120s，三者形成安全窗口（客户端 4 次心跳机会内任一成功即可续期）。

**Kafka 分区配置**（第5轮优化后）：

| 配置项 | 值 |
|--------|----|
| `welink.kafka.partitions.private-ingress` | 16 |
| `welink.kafka.partitions.group-ingress` | 16 |
| `welink.kafka.private-ingress-concurrency` | 16 |
| `welink.kafka.group-ingress-concurrency` | 16 |

### 8.2 降级

系统保留多级降级能力，用于关闭 presence、read receipt、大群推送或文件上传等功能。

## 9. 当前结论

当前消息链路已经验证通过：

- 私聊
- 小群/大群群聊
- 离线补偿
- 双实例跨实例群聊
- `message_outbox` 按桶批量写
- 消息持久化批处理（第5轮优化）：批量 INSERT + 并行 conversation UPDATE，p50 从 413ms 降至 8ms
- Redis Pipeline + Netty 调优 + 异步推送（第6轮优化）：5000 并发连接 0% 错误率，私聊 E2E 投递率 99.19%，吞吐量 7-8K msg/s

当前仍需继续推进的不是"链路不可用"，而是：

- 更高在线人数下的连接建立稳定性
- 多实例长期运行下的 outbox backlog 恢复能力
- 生产级流量入口与部署模板的进一步收口
- 群聊 E2E 测试工具优化（JMeter SingleReadWebSocketSampler 在高扇出场景下的读取效率限制）
