## 第 3 页：系统架构全景

**标题**：WeLink 系统架构

**内容**（架构图）：

```
客户端 (Vue3 + WebSocket)
    │ WS                    │ HTTP
    ▼                       ▼
Netty WS Server         Spring Boot HTTP
(8081端口)              (8080端口)
    │
    ├── Kafka 消息总线
    │     ├── im-private-ingress
    │     ├── im-group-ingress
    │     ├── im-private-message
    │     ├── im-group-message
    │     └── im-presence
    │
    ├── MySQL 8分片 (ShardingSphere)
    ├── Redis 7 (路由/缓存/限流)
    └── MinIO (对象存储)
```

**要点**：
- 前后端分离，WebSocket 实时推送 + HTTP REST API
- Kafka 解耦消息收发与持久化
- MySQL 8分片 × 64表 = 512 张消息表

## 第 9 页：问题分析 — P1 连接风暴

**标题**：问题一：高并发连接风暴

**现象**：5K 用户同时建连，连接超时率飙升

**分析**：
- TCP 半连接队列 (backlog) 默认 128，5K 并发瞬间溢出
- 认证阶段 Redis Pipeline 批量写入阻塞 IO 线程
- Netty 默认线程模型未分离 IO 与业务处理

**影响**：
- 连接建立失败 → 用户无法上线
- 认证阻塞 → 心跳超时 → 连接断开循环

---

## 第 10 页：问题分析 — P2 消息投递可靠性

**标题**：问题二：消息投递可靠性挑战

**现象**：吞吐测试"发完即忘"掩盖了 178K 次发布失败

**分析**：
- Kafka Producer 默认 delivery.timeout=120s，高负载下批量超时
- 消息静默丢失：Producer 发送失败后无重试兜底
- 跨实例消息依赖 Outbox 发布，但轮询扫描 O(512) 分片表

**影响**：
- 消息丢失用户不可感知
- Outbox 发布延迟 → 跨实例消息延迟

---

## 第 11 页：问题分析 — P3 双层限流冲突

**标题**：问题三：双层限流阈值倒挂

**现象**：私聊吞吐错误率 99.91%

**分析**：
```
WebSocketSession 限流: 100 req/s → 超限关闭连接 ❌
IMService 限流:       3000 msg/s → 超限返回错误
```
- 两层限流阈值倒挂：100 << 3000
- WS 层超限直接关闭连接，客户端无法重试
- 合法消息被误杀

**影响**：
- 几乎所有消息发送请求被 WS 层限流拦截
- 连接被关闭 → 客户端重连 → 再次被限流 → 恶性循环

---

## 第 12 页：问题分析 — P4 群聊扇出风暴

**标题**：问题四：群聊扇出风暴

**现象**：1 条群消息 → N 个成员 × M 个设备 → 推送积压

**分析**：
- 5000 人大群：1 条消息 → 最多 5000 × 3 = 15,000 次推送
- Redis 路由批量查询 + WS 推送争抢业务线程
- Consumer 积压 → Lag 增长 → E2E 延迟飙升

**影响**：
- 群消息延迟增大
- 系统资源被扇出推送占满

---

## 第 13 页：问题分析 — P5 分库分表写入瓶颈

**标题**：问题五：Outbox 轮询扫描瓶颈

**现象**：Outbox 发布任务扫描 512 张分片表，耗时过长

**分析**：
- message_outbox 按 target_user_id % 8 分库、% 64 分表
- 轮询时需扫描所有 512 张表查找 pending 消息
- HikariCP 连接池在 8 分片 × 64 表下连接泄漏

**影响**：
- Outbox 发布延迟
- 跨实例消息投递不及时

---

## 第 14 页：问题分析 — P6 服务降级缺失

**标题**：问题六：服务降级缺失

**现象**：高负载下所有功能争抢资源，系统雪崩

**分析**：
- 无降级策略 → 在线广播、已读回执、大群推送、文件上传全部运行
- 非核心功能占用大量 Redis/Kafka/数据库资源
- 核心功能（文本消息收发）被挤占

**影响**：
- 系统整体不可用
- 无法优先保障核心功能

## 第 15 页：技术方案 — P1 连接风暴

**标题**：方案一：Netty 线程模型优化 + TCP 参数调优

**措施**：
1. **SO_BACKLOG = 8192**：TCP 半连接队列扩大 64 倍
2. **IO/业务线程分离**：16 IO 线程 + 48 业务线程
3. **Redis Pipeline 批量写入**：认证时 3 个 Redis 命令合并为 1 次 Pipeline
4. **WriteBufferWaterMark**：[64KB, 256KB] 写缓冲水位线，防止 OOM

**效果**：
| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 5K 连接 P95 | >100ms | **2ms** |
| 认证 P95 | >500ms | **11ms** |

---

## 第 16 页：技术方案 — P2 Ingress-Consumer 架构

**标题**：方案二：Ingress-Consumer 可靠投递架构

**架构图**：
```
WS → Kafka Ingress → Consumer 持久化 → 本地推/Outbox
                                              │
                                    Outbox + Pending 索引表
                                              │
                                    Kafka Message → Consumer → 推送
```

**关键设计**：
- **Ingress 先入 Kafka**：消息不直接持久化，先进入 Kafka 保证不丢失
- **Consumer 持久化 + 推送**：Consumer 消费后原子性持久化 + 推送
- **Outbox 兜底**：跨实例消息写入 Outbox，定时轮询发布到 Kafka
- **Pending 索引表**：非分片表做轮询索引，O(1) vs O(512)
- **Redis Reconcile**：Pending 写入失败时 Redis 暂存补偿

## 第 17 页：技术方案 — P2 Kafka Producer 调优

**标题**：方案二（续）：Kafka Producer 参数调优

**参数对比**：
| 参数 | 默认值 | 优化值 | 说明 |
|------|--------|--------|------|
| acks | 1 | **all** | 确认所有副本 |

**效果**：发布失败次数大幅减少，Outbox 重试兜底保障最终一致

## 第 18 页：技术方案 — P3 统一限流

**标题**：方案三：统一限流层级 + 不关连接

**修复前**：
```
WebSocketSession: 100 req/s → 超限关闭连接 ❌
IMService:        3000 msg/s → 超限返回错误
```

**修复后**：
```
WebSocketSession: 500 req/s → 超限丢弃请求，不关连接 ✅
IMService:        500 msg/s → Redis 滑动窗口限流
```

**核心原则**：
1. WS 层仅做帧速率限制，**永远不因限流关闭连接**
2. 业务限流统一到 IMService 层，使用 Redis 滑动窗口
3. 限流阈值对齐：WS 层 > 业务层

**效果**：错误率 99.91% → **0.00%**

## 第 19 页：技术方案 — P4 扇出优化

**标题**：方案四：写扩散/读扩散自适应 + 并行推送

**策略**：
| 群规模 | 策略 | 推送方式 |
|--------|------|---------|
| ≤500 人 | 写扩散 | ForkJoinPool(32) 并行推 + Outbox 跨实例 |
| >500 人 | 读扩散 | Kafka 广播 + 各实例本地推 |

**优化措施**：
1. **ForkJoinPool(32)**：小群消息并行推送到所有在线成员
2. **Kafka 广播**：大群消息通过 `im-large-group-message` Topic 广播到所有实例
3. **每实例独立 Consumer Group**：确保所有实例收到大群消息
4. **降级 L3**：大群推送关闭时仅走读扩散

## 第 20 页：技术方案 — P5 Outbox Pending 索引表

**标题**：方案五：Outbox Pending 索引表 + 异步批量写入

**修复前**：
```
轮询扫描 512 张 message_outbox 分片表 → O(512) → 超时
```

**修复后**：
```
outbox_pending (非分片索引表) → HintManager 精确路由 → O(1)
```

**AsyncBatchWriter**：
- 内部队列 10,000 条
- 每 100ms 刷盘一次
- 按分片桶分组批量 INSERT
- 队列满时同步降级（单条写入）

**效果**：Outbox 发布延迟从秒级降至毫秒级

## 第 21 页：技术方案 — P6 五级降级

**标题**：方案六：五级降级策略

| 等级 | 关闭功能 | 保留功能 |
|------|---------|---------|
| **L0** 正常 | 无 | 全部功能 |

## 第 22 页：技术方案 — 分布式一致性

**标题**：分布式一致性保障

**机制**：
1. **Redis 路由表**：`im:route:user:{userId}` → 实例 ID，心跳续期 TTL 300s
2. **Kafka 跨实例投递**：每实例独立 Consumer Group，确保所有实例收到
3. **Outbox 兜底**：写入失败时 Pending 索引 + Redis Reconcile 双重补偿
4. **消息去重**：`im:dedup:client_msg:{clientMsgId}` Redis 5 分钟去重窗口
5. **会话序号**：`im:conv:seq:{conversationId}` Redis INCR 保证全局递增
